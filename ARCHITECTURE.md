# Personas system architecture

## Current boundary

The library remains a static Site. Persona content is the source of truth; the browser page is a renderer of that content.

```text
content/library-data/*.js + content/library-data.js + content/library-model.js
        |
        v
scripts/build-library.mjs
        |
        v
dist/data/*.js + dist/js/*.js + dist/*.html
        |
        v
private Sites deployment
```

## Source of truth

- `content/library-data/*.js` owns the authored Persona records, workflow maps, Skill profiles, resource trails, modular Skill guidance and practice overrides, primitive Skill units, typed Skill relationships, minimal Playbook identity and Template catalog records, Operating Pack catalog records and scoped applications, tool-use recipes, execution-grade Operational Scenario records, explicit Persona tool requirements, and Persona handoffs. The modules are grouped by coherent ownership and review size rather than one file per record. `content/library-data.js` is the small compatibility assembler: it verifies the required fragments, reconstructs the stable top-level `window.PersonaLibraryData` contract, and does not own the records themselves.
- `content/site-orientation.json` is the canonical machine-readable bootstrap for request modes, primary-space selection, universal policy, and the route-group index. `content/orientation/*.json` holds the selectively loaded route contracts grouped by existing primary space.
- `content/library-model.js` is the canonical normalizer. It derives stable skill IDs, merges persona-specific skill applications, maps workflow reach, resolves operating and quality guidance plus modular building blocks and related connections, attaches tool-use recipes and owner-scoped Operational Scenarios to the portable skills they make practical, provides targeted Operational Scenario matching, normalizes scoped Operating Pack and Template applications and source relationships, and filters persona tool requirements to known personas.
- `client/library-ui.js` owns shared browser render helpers for lists, resources, revision history, escaping, and trigger chips.
- `client/library-state.js` owns small URL-aware page state such as role filters, search terms, and selected records.
- `dist/data/library-data.js` is generated by concatenating the ordered authored modules under `content/library-data/` and the compatibility assembler. `dist/data/*.js`, `dist/data/site-orientation.json`, `dist/data/orientation/*.json`, and `dist/js/*.js` are generated output consumed by the Site pages and read-only consumers.
- `dist/index.html` owns persona presentation and page-specific interaction, not persona records or shared render primitives. Persona detail shows explicit tool requirements for architect and orchestrator activities, including capability, preferred path, mode, scope, fallback, and linked recipe context.
- `dist/skills.html` is the cross-persona Skills space: it indexes reusable capabilities and opens their triggers, operating model, quality signals, observable actions, workflow reach, evidence, modular anatomy, and persona applications.
- `dist/tools.html` is the first-class Tools space: it catalogs tools, research references, execution environments, and MCP adapters by capability, availability, scope, and risk. It also indexes representative tool-use recipes.
- `dist/tool.html` is the first canonical tool detail record. It demonstrates the execution-ready contract: capability, connector, workspace, permission, approval, verification, fallback, tool-use recipes, lessons, failure modes, and version history.
- `tool-discovery-and-safe-execution/` is a reusable skill for resolving a capability to the safest available tool or MCP, running a bounded probe, and promoting reviewed usage evidence into reusable guidance without silent permission or content changes.
- `tool-record-maintenance/` is a reusable skill for adding, updating, relating, reconciling, auditing, and retiring canonical tool records without executing tools or changing access.
- `persona-panel-orchestration/` is a reusable reasoning skill for consultations and panels. It requires explicitly named participants, processes each persona independently, preserves material disagreement, and synthesizes a clean response without silently updating durable records.
- `multi-perspective-skill-synthesis/` is the shared-capability formation gate: it compares distinct Persona evidence, checks Skill identity boundaries, and hands a bounded build brief to Persona Skills without silently mutating live records.
- `playbook-composer/` is the reusable Playbook composition layer: it defines an operating surface/process contract that coordinates canonical Personas, Skills, Tools, workflows, artifacts, state, decision rights, quality gates, recovery, and learning without executing the work.
- **Persona-operated Playbook invariant:** a Persona is the actor that exercises judgment and remains responsible for completion within its declared role. A Playbook supplies the process surface—stages, handoffs, state, gates, recovery, and learning—and must not be modeled as an autonomous owner or domain expert.
- `docs/collaboration/problem-context.md`, its schema, and `scripts/problem-context.mjs` define the file-based shared context MVP for multi-Persona work; the collaboration Playbook coordinates it without replacing canonical library records or providing a concurrent runtime.
- `eval/` is the repository-local conformance and resource-evidence layer. Subscription-backed task consumption is modeled separately from token/context evidence: `allowance-usage.md` and `allowance-usage.mjs` own normalized Work/Codex allowance snapshots, task deltas, caveats, and reporting, while `usage-telemetry.md`, `context-usage.mjs`, and provider adapters retain secondary token/context diagnostics. The adapters normalize supplied observations only; they do not sign in, scrape private account UI, make provider requests, buy credits, or imply that every runtime exposes the same meter. The repository has no production telemetry backend.
- `.agents/skills/persona-skill-conformance/` is the isolated Persona–Skill execution layer. It derives one case per canonical Persona Skill profile, uses a fresh low-reasoning task when the current runtime exposes task tools, captures quality and lifecycle evidence, and archives the temporary task. Its results remain separate from canonical Persona and Skill records.
- `change-impact-reconciliation/` is the universal post-change consistency protocol. Domain workflows call it after source, record, decision, prototype, or generated-artifact changes; `persona-reconciliation/` remains the Persona-specific adapter.
- `dist/playbooks.html` is the Playbooks space: it explains how personas, skills, workflows, artifacts, evidence, and quality gates compose around an outcome. Detailed playbooks can live behind it as deep links, such as `dist/job-search.html`.
- `dist/job-tracker.html` is the top-level Applications companion surface. `content/job-tracker-page.html` owns the UI, `client/job-tracker.js` owns page orchestration, and `client/job-tracker-store.js` isolates persistence. When deployment provides a Supabase URL and publishable key, real opportunity/application records live in authenticated private Supabase storage under RLS; otherwise the tracker runs in explicit browser-local fallback mode. Real rows are never canonical Persona-Library records or committed repository content. Versioned JSON and the storage adapter keep the surface extractable without migrating Persona or Skill identities.
- `dist/operating-packs.html` is the Operating Packs space: it catalogs reusable or project-specific Markdown-based operating context, shows source/location and availability, and exposes scoped Persona, Skill, workflow, Playbook, and related Tool-use relationships without embedding pack files or executing them.
- `.agents/skills/operating-pack-research/`, `.agents/skills/operating-pack-composer/`, and `.agents/skills/operating-pack-reconciliation/` own the proposal-first research, minimal Markdown composition, and read-only downstream review lifecycle for Operating Packs.
- `dist/templates.html` is the Templates browse space: it catalogs reusable starting artifacts and scaffolds, shows purpose, applicability, lifecycle, source evidence, runtime access, viewer representation, revision, and scoped relationships without executing or rendering external artifacts. `dist/template.html` is the focused Template viewer, reached with a stable Template ID, and presents the same normalized record plus explicit decision states for lifecycle, source, runtime access, and viewer representation.
- `.agents/skills/template-research/`, `.agents/skills/template-composer/`, and `.agents/skills/template-reconciliation/` own the proposal-first discovery, minimal composition, and read-only downstream review lifecycle for Templates.
- Persona and skill maintenance metadata records semantic revisions alongside file-level Git history.
- `dist/prototyping.html` is the active prototype index. It also owns isolated persona prototypes such as `proto-persona-surface-aware-partner`; these are test records, not live Personas, and must not affect counts, filters, shared skill catalogs, or production workflows until explicitly promoted.
- `dist/activity-views.html` and `dist/skill-views.html` are focused prototype detail surfaces; future experiments should be added here before they affect the current system.
- `dist/workflow-canvas.html` is the workflow canvas prototype (`proto-workflow-canvas-reasoning`). It reads persona workflow maps through `content/prototypes/workflow-canvas.js`, and reasons about a rearrangement using the portable `client/canvas-graph.js` diff and `client/canvas-intent.js` inference modules. Those two modules take a graph in and give a reading out with no library imports, so the capability can be extracted without unpicking it from the Site. The surface is read-only against live content: an intent reading is a hypothesis for a person to accept, never authorization to write.
- `workflow-canvas-reasoning/` is the prototype skill that owns that interpretation contract. It separates layout from meaning, attributes a change to the gesture that caused it rather than to the cards displaced by it, ranks readings by how well the structural change supports them, and reports what the canvas cannot express as open questions instead of resolving them by inference.
- `dist/guide.html` is the wiki for using the system, including the mental model and playbook composition rules. `dist/decisions.html` is the private archive of individually addressable decision records with status filters, prototype evidence, affected surfaces, and revisit conditions; `dist/job-search.html` is the first detailed playbook surface.
- `docs/decisions/records.json` is the single authored Decision collection. `content/decisions-page.html` is its presentation template, `scripts/build-decisions.mjs` renders the collection, and `dist/decisions.html` is generated output only.
- The `Persona Library Guide` is currently an isolated prototype. It is an onboarding and routing interface for newly connected LLMs; it prepares context and handoffs but does not become a live dependency until promoted through Decisions.
- `AGENTS.md` is the repository activation entry point. It points agents to the orientation bootstrap before they modify the project, then to the selected route group; the generated bootstrap and route groups under `dist/data/` serve the Site and other read-only consumers.
- `docs/job-search/implementation.md` is the scope and sequencing document for the job-search workspace. `dist/job-search.html` remains the responsive Playbook/reference surface and does not itself imply scraping, autonomous outreach, or mass submission. Persistent application lifecycle tracking is isolated in the separate Applications companion surface and uses browser-local private state rather than repository records.

## Docs, prototyping, and decisions boundary

Keep the three spaces complementary:

- Docs contain the current truth: definitions, boundaries, instructions, examples, prompts, and the current information architecture. They should be enough for orientation and reuse.
- Prototyping contains active experiments: alternative structures, interaction directions, sample content, and temporary comparison surfaces. It is safe to change or discard a prototype.
- Decisions contain the reasoning and history behind that truth: explorations, alternatives, tradeoffs, evidence, status, affected surfaces, and revisit conditions. They should make change understandable and accountable.

The working rule is: **Prototyping explores; Decisions archive; Docs explain what is true now.** Link a prototype to its decision record, link the decision to the Docs section or product surface it changed, and avoid copying whole explanations between the three spaces.

Docs provide the human-readable orientation page; the bootstrap and selected route groups provide the compact machine-readable contract. Keep them aligned through the build and validation checks rather than maintaining separate instructions by hand.

Work Orders are optional repository-wide execution/recovery packets for work whose existing authoritative surfaces do not preserve enough durable state to resume it. When present, they capture scope, evidence, decisions, gate status, handoffs, and next action without becoming a transcript or permission grant. The specialized artifacts remain distinct: problem-context coordinates shared Persona state, traceability matrices prove coverage, Decisions preserve durable rationale, prototypes explore, and issues or pull requests track implementation. See [Work Orders](docs/work-orders.md).

Use prototype status `Active → Selected → Archived`. Persona prototypes additionally use a `Testing` state and a promotion gate: representative test scenarios, observed behavior, open questions, and an explicit Decisions record before promotion. Use decision status `Proposed → Decided → Applied → Superseded`. Use `Parked` for a useful idea intentionally deferred.

The working rule for persona prototypes is: **prototype records can reference live personas and skills, but live records cannot depend on prototype records.** A promotion creates a deliberate change set and reconciliation pass; an archive leaves the live system untouched.

Each archived decision should preserve its question, chosen direction, rationale, tradeoffs, affected surfaces, source prototype, and revisit condition. A changed conclusion creates a new record and marks the previous record `Superseded`; it does not rewrite the old rationale.

The library now includes a contextual Operating Pack boundary: **Operating Packs describe the domain or project rules, standards, conventions, procedures, references, and validation guidance that govern work.** They can point to Markdown files in a local, project, external, planned, or unavailable source. A pack does not execute, install, or transport its files. Project context stays distinguishable from reusable best practice; repeated contextual rules can be handed to `persona-skills` for review, but they do not become Skill content automatically. Playbooks reference packs when an outcome needs that context instead of copying it.

Templates have a separate first-class boundary: **Persona-Library owns Template identity, applicability, relationships, source metadata, evidence, and lifecycle context. The reusable Template artifact may live externally. Templates provide a reusable starting structure or scaffold; they do not own reusable professional judgment, Operating Pack rules, Tool permissions, or Playbook orchestration.** A Template can be useful without an Operating Pack, and an Operating Pack can be useful without a Template. Repository existence, catalog presence, or a verified source revision does not prove that an individual external artifact exists or that the current runtime can access it.

The Template Librarian is the collection steward for that boundary: **the Persona keeps Templates findable, trustworthy, and current; routes discipline-specific research and composition to the relevant specialist; coordinates promotion, deprecation, relocation, and reconciliation; and escalates taxonomy, concept-boundary, and cross-library ownership questions to Mara Okoye.** The librarian does not own domain-specific professional judgment, Operating Pack methodology, Tool permissions, Playbook orchestration, or Persona-Library architecture.

Tools follow a separate boundary: **Tools describe what can act; Skills describe portable capability and quality; Persona tool requirements declare what an activity needs; Tool-use recipes bind a skill to a task in a specific tool; Personas describe why and when a person uses it; Playbooks coordinate the pieces toward an outcome.** A requirement is a capability need, not proof of availability. A recipe is not a new skill unless it contains independent reusable judgment. A tool record must not imply that a connector, credential, workspace, or permission is configured. A usage note is evidence of one attempt; only reviewed or repeated evidence can become shared guidance. Canonical data-backed Tool identities live in `content/library-data/tool-integration.js` under `toolCatalog` and use stable Tool IDs for recipe and Persona requirement relationships. Static Tools-page cards may coexist during migration, but they are presentation until backed by a canonical Tool record.

Callable Skills also carry a routing layer in their package metadata: `persona_applied` applies a capability to a target problem, `library_management` maintains system records, `orchestration` coordinates people and stages, `governance` reviews placement and downstream effects, and `tool_safety` resolves or exercises tool capabilities safely. The layer is a routing and ownership signal; it does not change the distinction between a Persona capability, a normalized Skill profile, a Tool, a workflow, or a Playbook. Non-callable workflows, templates, references, Decisions, prototypes, and Work Orders are classified by `artifact_kind` in the selected orientation route group. Keep the repository package layout flat until loader support for nested namespaces is proven.

Durable creation has a placement gate: **Mara Okoye, the knowledge systems architect, reviews whether a proposed Persona, Skill, Tool, Playbook, Doc, Decision, generated artifact, space, or file belongs as an extension of an existing record, relationship, workflow, recipe, or source file before a domain skill mutates it.** The review records the exact destination and closest alternatives; it does not grant write authority. Generated `dist/` files remain build outputs, never authoring destinations.

Change handling follows a universal boundary: **the workflow that performs the research or mutation owns the domain work; Change Impact Reconciliation checks the downstream consequences before handoff.** It is read-only by default, classifies dependents as confirms, extends, qualifies, contradicts, invalidates, or unrelated, and reports incomplete dependency visibility instead of pretending the review is exhaustive. Explicit relationships and declared artifact provenance are the supported dependency sources.

Every maintained skill declares a small change contract in its frontmatter: `skill_layer`, `change_mode`, `change_domain`, and `reconciliation`. Read-only skills skip the gate unless they create a durable artifact; prototype skills check isolation only; source-update, record-update, artifact-generation, and applicable external-execution skills invoke the universal gate; domain reconciliation adapters run once before the universal pass. Missing metadata falls back to read-only behavior and is reported as a contract gap.

Project context and reference routing is a Docs-owned method layered over the active work record and UX practice. It selects tagged project lenses and reference IDs without duplicating canonical Personas, Skills, Tools, Playbooks, or project evidence. Project-specific assumptions stay in the applicable Work Order, pull request, or linked context artifact; only reviewed, generalizable lessons may be promoted to shared Docs.

When repository work needs a dedicated execution/recovery packet, the default project artifact home is docs/work-orders/<work-order-id>/. A Work Order is optional: do not add one when Current Work plus the relevant issue/PR and domain-specific artifact already preserve the durable state needed to resume the work. The small-change lane in `docs/work-orders.md` is defined by that recovery-state footprint, not by semantic importance, file count, or whether a shared schema or governance surface changes. External project work stays in the external target.

## Repository placement and lifecycle

Current reusable guidance is grouped under docs by subject. Active Work Order packages stay in docs/work-orders/<work-order-id>/ when a dedicated execution/recovery packet is warranted; terminal Work Orders move to docs/work-orders/archive/YYYY-MM/<work-order-id>/ without deleting history. The repository-local Skill namespace remains flat, content/ and client/ remain authored sources, `docs/decisions/records.json` is the authored Decision collection, and dist/ remains generated output that must be rebuilt rather than hand-edited. See docs/README.md for the placement gate and lifecycle table.

## Invariants

Run `node scripts/build-library.mjs` after changing content or client modules, then run `node scripts/validate-content.mjs` before publishing. The build composes the ordered authored modules under `content/library-data/`, expands Operational Scenario source paths from their compact index, and appends the compatibility assembler into `dist/data/library-data.js`; no generated data file is an authoring destination. The top-level validator loads that same composed source data and indexes once, then delegates to focused modules under `scripts/validation/`: orientation and Skill package contracts, generated output and Site contracts, Persona records and workflows, Skill profiles and units, explicit cross-domain relationships, Operating Packs, Templates, and semantic maintenance metadata. The focused modules enforce canonical contracts without becoming a second source of authored truth; `validate-content.mjs` remains the single top-level command and report.

Focused regression cases live beside those modules at `scripts/validation/validation.test.mjs`. They prove representative Persona, Skill, and cross-domain failures without loading unrelated generated presentation files. Use `node --test scripts/validation/validation.test.mjs` for that bounded check, followed by the top-level validator for full repository coverage.

Counts and filters should be derived from the content module. Do not hand-edit persona totals or role totals as the library grows.

## When to expand the stack

Keep the static-first architecture for canonical library content: Personas, Skills, Tools, Templates, Operating Packs, Playbooks, Docs, Decisions, and Work Orders remain authored in Git. Applications is the first approved exception for operational persistence: private opportunity rows may live in authenticated Supabase storage behind a storage adapter because agent access, cross-device persistence, and recoverability now exceed the browser-local MVP. Browser-local state remains an explicit migration/offline fallback rather than the remote store's silent failure path. Future Supabase catalog tables are read-only projections from Git unless a later Decision explicitly changes the authoring boundary. Keep ordinary page state in the URL-aware helper until state must persist across users or sessions.

## Operational knowledge boundary

Execution-grade best practice is stored as structured `operationalScenarios` attached to existing Skills or Tool-use recipes. Authored scenario bodies live one-per-file under `content/library-data/operational-scenarios/`, with `index.json` as the compact routing manifest. A scenario can add concrete do/don't guidance, recommended sequence, state reuse, freshness triggers, stopping/escalation conditions, good/bad traces, recovery, and evidence status without creating a new Persona, Skill, Tool, Playbook, or top-level knowledge space.

The normalizer exposes owner-scoped scenario relationships and `findOperationalScenarios` for targeted matching. Repository agents should resolve the owner, read only the routing manifest, and fetch the selected scenario body rather than the whole authored catalog. The build may concatenate all scenario sources into the generated browser bundle because generated runtime composition does not consume agent context. Applicable Operating Packs retain authority for project/domain-specific constraints, and scenario guidance never grants Tool permission or replaces current live-state verification.

Existing `docs/internal/skill-rebuild/tests/*.golden.md` files remain focused callable-Skill test fixtures. They may validate similar behaviors but are not the canonical operational knowledge source.
